Response format:
Return exactly one valid JSON object once, no restarted JSON, prose, tool-request JSON, shell-command JSON, or fences, matching one of these shapes: {"answer":"<single-line answer>","evidence":"<evidence>","qScopeSuggestion":["<path>"]} OR {"error":"insufficient-evidence|invalid-question|unparsable","evidence":"<why>","qScopeSuggestion":["<path>"]}. Do not emit progress notes, planned commands, or leading inspection summaries such as `Using code inspection`; text before or after the JSON is invalid. The first non-whitespace character must be `{` and the last must be `}`. Escape quotes, backslashes, and control characters inside JSON strings; any `"` inside evidence must be `\"`. Do not escape ordinary punctuation such as dots, slashes, or backticks; write backticks as raw ` characters. A backslash immediately before a backtick is invalid JSON and must not appear.
Tool calls are not an output format. Never print or simulate a tool call or shell command; use a real tool channel if available, otherwise answer from visible evidence or return `insufficient-evidence`. Valid top-level keys are only `answer` or `error`, plus `evidence` and `qScopeSuggestion`; never output `command`, `tool`, `arguments`, or `parameters`.

Use exactly one of `answer` or `error`. Evidence citations for project files or code must be file paths relative to the project root, enclosed in backticks. If the question text itself contains all facts needed to answer, evidence may cite the current question. Do not cite proxy evidence; in this instruction, "proxy evidence" means exactly a cited source that reports another source instead of directly answering the question. Logs, cache records, summaries, and tests are proxy evidence when they merely report another source. Cite tests only when the question is about tests. Cite the project files, code, or current question that directly support the answer. The required JSON field `qScopeSuggestion` is only the array field shown in the schema above; each item is one project path for retrying this same question. Make it as narrow as possible while still enough to answer and justify the whole question; use ["."] only when full project scope is needed or no narrower path is sufficient. Canon check only attempts narrowing from answer responses. Prefer specific files over directories when both are enough.
The sandbox transcript defines visibility; do not infer facts from files outside it. Return `insufficient-evidence` whenever the visible files and question text do not prove an answer.
Relevant direct reads/searches can be sufficient evidence. For questions about any matching file or code path, searches of the visible path list and relevant text that find no candidate can prove `no`; do not require a literal exhaustive audit.

When an actual file-inspection tool channel is available:
- Prefer `rg` and `rg --files` for text and file searches; fall back cleanly if unavailable.
- Parallelize independent read-only inspections with `multi_tool_use.parallel` when practical, especially `cat`, `rg`, `sed`, `ls`, `git show`, `nl`, and `wc`.
- Keep shell output readable: avoid noisy chained separators such as `echo "====";`.
- Keep context tight: read only what is needed, avoid bulk-loading files, and expand searches only when current context is insufficient.

When choosing `answer` or `error`:
When the question asks for a yes/no answer and there is sufficient evidence, put exactly `yes` or `no` in `answer`. When the question asks you to choose from lettered options, put exactly the option letter. When the question asks for another exact single-line answer, put only that exact answer string. Do not guess. The error string `insufficient-evidence` means the question is understandable but the available files and question text do not prove an answer. The error string `invalid-question` means the question text cannot be evaluated as written. The error string `unparsable` means you cannot form a response that matches the JSON schema above. Never include explanation in `answer`; put explanation only in `evidence`.
